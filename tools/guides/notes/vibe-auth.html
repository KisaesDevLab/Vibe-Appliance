What changes when you enable it — and what does not. Vibe Auth is the appliance's identity broker: staff sign in once, with MFA, and every Vibe app you connect to it accepts that session. Enabling it changes nothing about how anyone signs in today. Each app keeps working on its own local accounts until you connect it and then choose its sign-in mode, one app at a time.

Order of work

  1. Enable Vibe Auth from its card. First start takes longer than other apps (up to five minutes) because the bundled identity server applies its configuration before the health check turns green. Do not click Enable again while the badge says enabling…; the card tells you if it actually failed.
  2. Run the setup wizard (previous section) from the admin console's Single sign-on (Vibe Auth) panel. Enrol MFA for the first administrator when the wizard asks. The Vibe Auth admin console is then at …/auth/if/admin/ on the appliance address.
  3. Create the firm's staff in the Vibe Auth admin console, or connect the firm's Microsoft Entra ID / Google Workspace so staff sign in with the accounts they already have. Put each person in the group that matches their role (for example vibe-partner, vibe-staff); apps map those groups to their own roles.
  4. Connect each app. In the Single sign-on panel every SSO-capable app has a card. Click Register. The appliance registers the app with the broker, restarts it, and creates a local emergency account in it named vibe-breakglass. Nothing else changes yet — the app still uses local sign-in.
  5. Switch the sign-in mode on that card, in this order:
    ModeWho can sign inWhen to use it
    localLocal accounts only (today's behaviour).Default after registering.
    bothLocal accounts and the SSO button.Roll-out. Have every staff member sign in once through SSO before moving on.
    oidc_onlySSO only, plus vibe-breakglass.Steady state. Local passwords stop working for everyone else.

Before you choose oidc_only for any app, save its break-glass password. It is in /opt/vibe/CREDENTIALS.txt on the server (line VIBE_BREAKGLASS_PASSWORD_<APP>) and in the app's Register output. Put it in the firm's password manager. It is the only way into that app if Vibe Auth is down, and the console refuses oidc_only until a break-glass account exists.

Apps enabled later

An SSO-capable app you enable after Vibe Auth is running registers itself automatically during its own enable. It still starts in local mode; switch it when you are ready. If a card shows not registered even though Vibe Auth is healthy, click Fix registration — it is safe to repeat.

Things that happen rarely

  • The server's name, IP, domain or routing mode changed. Click Re-derive issuers at the top of the Single sign-on panel. Until you do, SSO sign-ins fail with a redirect error while local sign-in keeps working.
  • Rotate secret on an app card issues that app a new client secret and restarts it. Use it if the app's configuration file was ever shared or copied.
  • Disable SSO on an app card returns just that app to local sign-in. Disabling Vibe Auth itself first returns every connected app to local sign-in, so nobody is locked out, then stops the broker. Re-enabling later reconnects them; their modes start back at local.
  • Someone left the firm. Disable them in the Vibe Auth admin console and end their sessions there; connected apps drop their session at the next request. Also remove any local accounts they had in apps still running in local or both mode.
  • Password recovery mail uses the appliance's Email settings (Settings → Email & SMS). Without SMTP, an administrator resets passwords in the Vibe Auth admin console instead.

Emergency access

The emergency port reaches the broker's status page only. Single sign-on itself needs the normal web front end (the /auth/ route), so if the front end is down, sign in to each app with its vibe-breakglass account until the doctor has the front end back.
